# Specification 01: Core Runtime Integrity & Durability (Phases 0–2)

## Problem Statement

When deploying applications generated by Foundation to multi-replica production environments, developers encounter discrepancies between the operational promises made in the Blueprint and the guarantees delivered by the runtime:
- Tactical traits like `@idempotent` and `@cache` use per-process in-memory maps, allowing concurrent requests on different replicas to execute duplicate mutations or double-charge transactions.
- The `@outbox` trait buffers events in volatile memory without database persistence; if a node restarts or crashes before flushing, business events vanish permanently.
- Entity mutations overwrite database rows with no concurrency control (last-write-wins), causing silent lost updates when multiple users or processes concurrently edit the same entity.
- The `@cron` trait lowers without distributed leader election, causing scheduled jobs to double-fire under multiple replicas.
- The `@event_handler` trait is recognized by the compiler but lacks an emitted execution dispatcher to trigger handlers when domain events are published.
- The Go backend target emits no runnable entrypoint (`main.go`), forcing developers to handwrite server initialization and signal handling before they can run their service, creating an unnecessary discrepancy with the TypeScript target.
- Tactical trait plumbing is emitted inline, meaning any bug fix or enhancement to runtime behavior requires recompiling the entire application and regenerating source code.

## Solution

Deliver the Core Runtime Integrity & Durability milestone (Phases 0, 1, and 2) across the compiler and generated targets:
1. Establish a **versioned Contrib Runtime Library** architecture (`contrib/go/runtime` and `contrib/ts/runtime`) with swappable storage drivers (`memory` and `postgres`), shifting runtime state and infrastructure behavior out of emitted templates into maintainable, version-pinned dependencies.
2. Provide a **zero-dependency memory driver** for the contrib libraries, ensuring that declarative Scenarios and Contract Tests run 100% offline in `foundation test` with zero external network access.
3. Enforce **honest grammar**: cut `@cron` with a clear compile-time parse diagnostic reserving the keyword until true cluster leader election is implemented.
4. Emit a **synchronous post-commit in-process Event Dispatcher** that triggers `@event_handler` Actions in declaration order after the emitting Action's transaction commits, with handlers executing as independent Actions governed by their own policies, retries, and transactions.
5. Emit a manifest-tracked **runnable Go server entrypoint** (`cmd/server/main.go`) with graceful shutdown (`SIGINT`, `SIGTERM`), environment variable configuration, and database connection pooling, achieving operational parity with TypeScript's `server.ts`.
6. Implement **Optimistic Concurrency Control (OCC)**: support the `@version` field trait on entities, compile `update` statements to conditional SQL increments (`WHERE id = $1 AND version = $2`), detect concurrent conflicts, return a built-in `conflict` error kind (HTTP 409), and emit `ETag` and `If-Match` headers.
7. Persist `@idempotent` keys and `@outbox` events directly into PostgreSQL tables within the action's database transaction to guarantee at-least-once delivery and zero duplicate executions under node failure.

## User Stories

### Contrib Runtime & Offline Testing (Phase 0)
1. As a platform engineer, I want the compiler to generate dependencies against published, versioned contrib runtime libraries (`contrib/go/runtime` and `contrib/ts/runtime`), so that runtime infrastructure bugs can be patched via dependency updates without requiring compiler upgrades or project regeneration.
2. As a platform engineer, I want the compiler to verify SemVer compatibility between the compiler binary and pinned contrib runtime libraries at build time, so that version drift is caught before deployment.
3. As a developer running tests in air-gapped CI or on an offline laptop, I want `foundation test` to run against a zero-dependency in-memory driver, so that Scenarios and Contract Tests execute hermetically without downloading external packages.
4. As a developer, I want the Generation Manifest to exclude dependencies and runtime locks from destructive pruning, so that package management remains standard across target ecosystems.

### Honest Grammar & Event Dispatch (Phase 1)
5. As a domain author, I want the compiler to reject `@cron` with an informative error stating the trait is reserved until cluster leader election is implemented, so that I am never misled into believing an un-coordinated ticker is safe for multi-replica production.
6. As a domain author, I want to declare `@event_handler(EventName)` on an Action, so that the Action is automatically invoked whenever the subscribed event is emitted within the application.
7. As a backend developer, I want event handlers to execute strictly *after* the emitting Action's database transaction successfully commits, so that handler failures never roll back already-committed business state.
8. As a backend developer, I want event handlers to execute in declaration order within the emitting process, so that in-process workflows progress deterministically.
9. As a domain author, I want event handler Actions to support their own policies, `@retry`, and `@transactional` traits, so that each handler controls its own operational robustness.
10. As a domain author, I want to write declarative Scenarios for event handlers that verify their execution when an event is published, so that asynchronous reactive behavior is fully testable.

### Runnable Go Server Entrypoint (Phase 1)
11. As a Go developer, I want `foundation build` to scaffold a manifest-tracked `cmd/server/main.go`, so that I can immediately boot my service using `go run ./cmd/server` without writing manual bootstrap code.
12. As a Go developer, I want the emitted `main.go` to parse standard environment variables (`PORT`, `DATABASE_URL`) with sane defaults, so that the application is twelve-factor compliant out of the box.
13. As a site reliability engineer, I want the emitted Go server to intercept `SIGINT` and `SIGTERM` signals and execute a graceful shutdown with a bounded deadline, so that in-flight requests complete cleanly during rolling deployments.
14. As a Go developer, I want the generated Go server to maintain feature parity with the TypeScript server (`server.ts`), so that multi-target architectures behave consistently.

### Durable Tactical Traits & Concurrency Control (Phase 2)
15. As a domain author, I want to annotate an integer field on an Entity with `@version`, so that the compiler enforces Optimistic Concurrency Control during entity updates.
16. As a domain author, I want the compiler to validate that an Entity declares at most one `@version` field and that the field is of type `int`, so that invalid concurrency models are caught at compile time.
17. As a backend engineer, I want emitted PostgreSQL update queries for versioned entities to execute `WHERE id = $1 AND version = $2` and atomically increment the version, so that stale updates affect zero rows.
18. As a backend engineer, I want an update that affects zero rows due to a version mismatch to raise a built-in `conflict` error, so that concurrent mutations never overwrite state silently.
19. As an API consumer, I want concurrent mutation conflicts to return an HTTP 409 Conflict status code, so that my client knows to refresh the entity and retry.
20. As a frontend engineer, I want GET requests for versioned entities to return an `ETag` HTTP header derived from the entity version, so that clients can track cached entity freshness.
21. As a frontend engineer, I want mutating HTTP endpoints for versioned entities to evaluate the incoming `If-Match` header, so that clients can guarantee they are updating the version they read.
22. As a backend engineer, I want actions with `@idempotent` in PostgreSQL mode to record idempotency keys in a durable database table within the same transaction as entity mutations, so that duplicate requests across multiple replicas return the original cached response without re-executing.
23. As a backend engineer, I want actions with `@outbox` in PostgreSQL mode to insert domain events into an outbox database table inside the action transaction, so that events are guaranteed to persist even if the application node crashes immediately after commit.
24. As a site reliability engineer, I want a background outbox relay in the contrib runtime to poll and publish unhandled events from the outbox table, so that at-least-once delivery is maintained across process crashes.

## Implementation Decisions

### 1. Module Boundaries & Package Organization
- **Contrib Runtimes**: Placed in the project monorepo under `contrib/go/runtime` and `contrib/ts/runtime`. Each provides an identical driver abstraction:
  - `IdempotencyStore`: `GetOrLock(ctx, key, ttl) -> (Status, Value, UnlockFunc)`
  - `OutboxStore`: `Stage(ctx, tx, event) -> error` and `Relay(ctx) -> error`
  - `CacheStore`: `Get(ctx, key)`, `Set(ctx, key, val, ttl)`, `Delete(ctx, key)`
- **Stage 1 (Frontend & Validation)**:
  - Lexer/Parser: Update grammar to flag `@cron` as an illegal/reserved trait token (`FDN0115`).
  - Validation: Add rule verifying that `@version` is only applied to an `int` field on an `entity`, and that at most one `@version` field exists per entity.
  - Diagnostics: Add `conflict` to the built-in `ErrorKind` enumeration.
- **Stage 2 (Architecture Lowering)**:
  - `ArchitectureIR`: Update Action representation to lower `@event_handler` subscriptions into an internal event routing table.
  - Update `TargetFile` generation to include `cmd/server/main.go` for Go targets (`hexagonal` and `layered`).
  - Lower `update` steps for versioned entities to include expected version arguments and increment logic.
- **Stage 3 (Emitters)**:
  - Go Emitters (`emit/gohex`, `emit/golayered`): Emit `cmd/server/main.go`, integrate contrib runtime ports, emit OCC update queries (`AND version = $expected`), and generate HTTP 409 mapping.
  - TypeScript Emitter (`emit/tsclean`): Emit OCC update checks, integrate TypeScript contrib runtime, and map `conflict` errors to HTTP 409.
  - PostgreSQL Emitter: Emit `schema.sql` and migrations with `idempotency_keys` and `outbox_events` tables when corresponding traits are used, and include version columns.

### 2. Event Dispatching Semantics
- In-process event dispatcher is generated directly in the bootstrap container.
- When an Action emits an event:
  1. The Action executes its pipeline and commits its database transaction (if `@transactional`).
  2. The container invokes the internal dispatcher passing the committed event.
  3. The dispatcher invokes subscribed handler Actions sequentially in declaration order.
  4. Each handler opens its own execution context, evaluates its own policies, and manages its own transaction.

### 3. Optimistic Concurrency Control SQL Contract
- Versioned Entity Schema:
  ```sql
  CREATE TABLE orders (
      id UUID PRIMARY KEY,
      version INTEGER NOT NULL DEFAULT 1,
      ...
  );
  ```
- Versioned Update Execution:
  ```sql
  UPDATE orders
  SET status = $1, total = $2, version = version + 1
  WHERE id = $3 AND version = $4
  RETURNING version;
  ```
- If rows affected == 0, the repository raises `ErrConflict`, mapped by the pipeline to the built-in `conflict` error kind.

## Testing Decisions

- **Testing Seam**: The highest possible public compiler interface — `compiler.Build` and `compiler.Test`.
- **Hermetic Unit Tests**:
  - Compiler tests assert that Blueprints with `@cron` fail fast at Stage 1.
  - Compiler tests assert that Blueprints with invalid `@version` usage (multiple version fields, non-int types) fail at Stage 1.
  - Generated workspace tests (`go test` and `node --test`) verify that Scenarios executing event emissions properly trigger event handlers in-memory.
  - Generated workspace tests verify that concurrent version updates in memory trigger `conflict` errors.
- **PostgreSQL Integration Tests**:
  - Test suite in `pkg/compiler` runs a generated backend against testcontainers/local PostgreSQL to verify that `idempotency_keys`, `outbox_events`, and OCC `WHERE version = $2` queries execute correctly and rollback safely.

## Out of Scope

- External message broker adapters (Kafka, RabbitMQ, SQS) — deferred to post-1.0 contrib adapters.
- Distributed cron scheduler with leader election — explicitly deferred until a consensus story (e.g. Raft or Postgres row lock) is designed.
- Dynamic runtime migration execution CLI (`foundation migrate`) — migrations remain generated SQL files.
- Authentication and Actor resolution — specified in Specification 02.
- `query many` list querying — specified in Specification 02.

## Further Notes

All additions in this specification preserve full backward compatibility for Blueprints that do not declare `@version` or `@event_handler`. The Generation Manifest strictly tracks all new emitted files, including `cmd/server/main.go`.
